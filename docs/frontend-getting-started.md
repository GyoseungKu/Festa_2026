# 프런트엔드 연동 시작하기

[문서 목차](README.md) · [공통 API 규약](frontend-api-common.md) · [전체 API 색인](api-endpoint-index.md)

사용자 웹을 처음 구현할 때의 작업 순서입니다. 요청 필드·응답 타입·오류 코드는 연결된 기능별 문서에서 확인합니다. 서버 실행이 필요하면 루트 [README](../README.md)의 로컬 실행 안내를 먼저 확인합니다.

## 1. API 연결과 공통 요청 처리

연동할 서버의 Base URL과 프런트 Origin을 먼저 정합니다. 로컬 서버 기본 포트는 `8888`입니다. 프런트와 서버의 Origin이 다르면 서버의 CORS 허용 설정과 쿠키 전달 조건을 함께 확인합니다. 문서의 `/api/...`는 백엔드 기준 경로입니다.

[공통 API 규약](frontend-api-common.md)의 fetch 래퍼를 프로젝트의 토큰 저장소와 연결합니다. 모든 화면에 다음 처리를 공통으로 적용합니다.

- 인증·학교 세션 요청은 `credentials: "include"`를 사용하고, 로그인한 사용자의 요청에는 메모리 Access Token을 Bearer 헤더로 전달합니다.
- 응답의 `X-Access-Token`으로 메모리 토큰을 교체합니다.
- 본문 없는 `200`과 `204`는 JSON 파싱을 생략합니다. 실패는 HTTP 상태와 응답 `code`를 함께 확인합니다.
- `401` 인증 실패, `403` 권한·정책 제한, `429` 요청 제한을 구분합니다. `Retry-After`를 반영하고 작성·신고 같은 변경 요청을 무조건 재전송하지 않습니다.

첫 연결 확인은 공개 API인 `GET /api/booths`로 진행합니다. 응답 타입과 선택적 인증에 따른 찜 표시는 [부스 API](frontend-booths-api.md)를 확인합니다.

## 2. 로그인과 새로고침 후 복구

1. [인증 API](frontend-auth-api.md)의 로그인 요청으로 Access Token을 받고 메모리에 저장합니다. Refresh Token은 서버가 HttpOnly 쿠키로 설정합니다.
2. Bearer 헤더로 `GET /api/users/me`를 호출하고 [내 정보 응답](frontend-user-api.md)의 권한·학생 인증 상태에 맞춰 화면을 구성합니다.
3. 새로고침으로 메모리 토큰이 사라지면 `POST /api/auth/token/refresh`를 먼저 호출합니다. 성공 후 보호 API를 요청합니다. Refresh 쿠키만 붙여 보호 API를 바로 호출하는 방식은 지원하지 않습니다.
4. 복구 중에는 인증 확인 상태를 표시합니다. 인증 실패가 확정되면 비로그인 상태로 전환하고, 네트워크·서버 오류는 재시도 가능한 오류로 구분합니다.
5. 로그아웃은 서버 API 호출 후 메모리 토큰과 사용자별 캐시를 정리합니다.

축제 권한과 SSO 권한은 별개입니다. 버튼 노출을 숨기는 것만으로 권한 검증을 대신할 수 없으며, 서버의 거부 응답도 처리해야 합니다.

## 3. 가입·계정 화면 연결

| 화면 | 읽을 문서 | 구분할 내용 |
|---|---|---|
| 회원가입 | [인증 API](frontend-auth-api.md) | 아이디 4~50자, 이메일 인증, 중복 확인, 최종 제출 검증 |
| 학교 학적정보 입력·학생 인증 | [학교 SSO](frontend-school-sso.md) | 가입 전 학적정보 입력과 로그인 후 학생 인증의 진입 경로·콜백 처리 |
| 아이디 찾기·비밀번호 재설정 | [계정 복구](frontend-account-recovery-api.md) | 비로그인 복구 절차 |
| 마이페이지·이메일·탈퇴 | [내 정보](frontend-user-api.md) | 축제 서비스 이용 정보 삭제와 SSO 계정 탈퇴의 대상·보존 범위 |
| 로그인 후 비밀번호 변경 | [비밀번호 변경](frontend-password-change-api.md) | 계정 복구와 다른 요청·검증 |

학교 SSO 콜백 성공은 Festa 로그인 성공과 같은 의미가 아닙니다. 학교 연동 문서의 흐름에 따라 가입 또는 학생 인증 단계를 이어갑니다.

## 4. 기능별 화면 연결

| 구현할 화면 | 문서 | UI에서 먼저 확인할 계약 |
|---|---|---|
| 홈·배너·공지 상세 | [공지](frontend-notices-api.md) | 배너 필터·페이지네이션, 상세 조회수 증가, 미디어와 파일 배열 |
| 지도·부스 상세·찜 | [부스](frontend-booths-api.md) | 좌표, 대표 미디어 null, 로그인 여부에 따른 찜 |
| 공연 일정 | [공연](frontend-performances-api.md) | 시간·미디어 응답 |
| 협찬사 | [협찬사](frontend-sponsors-api.md) | 사진·부스 연결 |
| 내 QR·스탬프판·지급 화면 | [QR](frontend-qr-api.md), [스탬프](frontend-stamps-api.md) | 토큰 갱신, 스캔 목적별 API, 담당 부스·권한 |
| 투표·설문 | [투표](frontend-polls-api.md) | 문항 종류, 제출 가능 조건, 결과 공개 조건 |
| 분실물·생일축하 | [분실물](frontend-lost-items-api.md), [생일축하](frontend-birthday-messages-api.md) | 페이지네이션·작성 권한·내 글·하트 |
| 익명 채팅 | [대나무숲](frontend-bamboo-api.md) | 닉네임 확정, 과거/변경 커서 구분, ID 기준 갱신, 작성 간격 |
| 화면 분석·접속 현황 | [분석 이벤트](frontend-analytics-api.md), [Presence](frontend-presence-api.md) | 이벤트 버퍼·heartbeat 주기·개인정보 제외 |

채팅의 신고 누적 `HIDDEN`은 원문이 제공되므로 가림·펼치기를 구현합니다. 관리자 차단 `BLOCKED`와 삭제 `DELETED`는 원문이 null이며 화면의 기존 원문도 제거합니다. 상세 조건은 대나무숲 문서의 상태 표를 따릅니다.

파일 업로드 화면을 구현할 때는 [업로드 규약](api-upload-limits.md)에서 기능별 파트 이름·파일 개수·용량을 먼저 확인합니다. `FormData`의 `Content-Type`은 직접 지정하지 않습니다. PATCH가 부분 수정인지, 필수값 재전송이 필요한지는 각 기능 문서를 확인합니다.

## 5. 사용자 API와 관리자 웹 구분

기능별 문서의 관리 REST API는 명시된 축제 권한이 있어야 합니다. 서버에서 렌더링하는 `/admin/**` 페이지는 별도 관리자 쿠키와 CSRF 규칙을 사용합니다. 사용자 프런트의 Bearer 요청 코드를 그대로 적용하지 말고 [관리자 웹 경로](admin-web-api.md)를 확인합니다.

DB 스키마·환경변수·배포 절차는 서버 운영 담당자가 확인할 내용입니다. [문서 목차](README.md)에서 사용자 연동 문서와 운영 문서를 나누어 찾을 수 있습니다.

## 6. 연동 완료 확인

- 비로그인 조회, 로그인, 새로고침 복구, 로그아웃 후 사용자 캐시 초기화를 확인합니다.
- 빈 목록·마지막 페이지·nullable 필드·권한 부족·인증 만료·요청 제한을 확인합니다.
- 날짜와 시간의 타입을 구분하고, 사용자 입력은 HTML로 삽입하지 않고 텍스트로 렌더링합니다.
- 채팅은 신고 누적·관리자 차단·복구 시 이미 표시한 메시지가 갱신되는지 확인합니다.
- 요청·응답 상세는 기능별 문서와 Swagger UI(`/swagger-ui.html`)를 대조합니다. Swagger에 표현되지 않는 서비스 정책도 기능 문서에서 확인합니다.
